# 内容与平衡提案（2026-10-18，待拍板）

> 本文只提方案与实测数据，**未改动 `NPCManager.gd` / 数值 / 场景**。
> 所有数字都可用文末命令复现；候选字已逐个核对字体覆盖。

## 一、现状：内容量

| 项 | 当前值 | 出处 |
|---|---|---|
| 信型 | 5（家书 / 请安 / 贺寿 / 诉苦 / 求荐）| `NPCManager.LETTER_TYPES` |
| 关系 | 5（父母 / 子女 / 夫妻 / 兄弟 / 朋友）| `NPCManager.RELATIONS` |
| 称谓池 | 3 / 关系（共 15 条）| `SALUTATION_POOL` |
| 落款池 | 3 / 关系（共 15 条）| `SIGNATURE_POOL` |
| 正文词库 | 6 / 槽 × 3 槽 × 5 信型（共 90 个位置）| `BODY_POOLS` |
| 故事模板 | 16 条（家书 4 / 其余各 3）| `STORY_TEMPLATES` |
| 一局委托数 | 10 天 × 3 = **30 单** → 平均每种信型出现 **6 次** |

**问题**：单信型平均 6 单、模板 16 条，玩到第 3 天就能感觉"这几个故事见过"；
正文每槽只有 6 个候选，记性好的玩家可以背答案（虽然故事文本每次随机嵌入正解，仍有"读故事"这一层）。

## 二、现状：数值（`node tools/balance_sim.mjs`，20000 局）

| 策略 | 成功率 | 终局钱 p50 |
|---|---|---|
| 最优（每槽必中）| 100% | **771** |
| 熟练（90% 命中）| 100% | 687 |
| 一般（75% 命中）| **69.5%** | 522 |
| 粗心（60% 命中）| 0.2% | 375 |
| 偶尔留空（90% + 5% 空槽）| 60.9% | 517 |
| 不看故事（池内随机）| 0% | 225 |

**结论**：① "读懂故事"是硬门槛（随机猜 0%），符合设计意图；
② 但**完美线太宽**——全对能到 771，目标 500，盈余 54%，终局没有紧张感；
③ 难度悬崖在 60%–75% 命中之间，很陡。

### 目标金额细扫（其余参数不变）

| 目标 | 最优 | 90% | 75% | 60% | 随机 | 最优终局 p50 |
|---|---|---|---|---|---|---|
| **500（当前）** | 100% | 100% | 68.9% | 0.1% | 0% | 771 |
| 525 | 100% | 100% | **47.2%** | 0% | 0% | 771 |
| 550 | 100% | 100% | 24.8% | 0% | 0% | 771 |
| 575 | 100% | 100% | 10.1% | 0% | 0% | 771 |
| 600 | 100% | 99.7% | 2.9% | 0% | 0% | 771 |

另测：`--bonus-mul 0.75`（完美加成打七五折）→ 最优 p50 677、90% 仍 100%、**75% 掉到 21.0%**。
**单改 bonus 太狠**，不如调目标。

## 三、三个方案

### 方案 A：内容扩充（**推荐**，不改数值）

| 项 | 现在 → 提案 |
|---|---|
| 正文词库 | 6 → **10** / 槽（每信型 +12 词）|
| 称谓池 | 3 → **5** / 关系 |
| 落款池 | 3 → **4** / 关系 |
| 故事模板 | 16 → **26** 条 |

- **数值影响 ≈ 0**：模拟里的"命中率"是玩家能力参数，与词库大小无关；
  但**瞎蒙更难**（每槽 1/6 → 1/10），"偶尔蒙对"会减少 —— 方向正确。
- **必须同时改一处 UI**：`letter.gd::_build_word_pools()` 现在是**每个正文槽一个 HBox**，
  6 个按钮刚好占满左栏；变 10 个会横向溢出。
  改法：把该行的 `HBoxContainer` 换成 `HFlowContainer`（自动换行），**改完必须重截代写界面**。
- 候选词表已备好：[`data/content_candidates_2026-10-18.json`](../data/content_candidates_2026-10-18.json)，
  **85 条、181 个不同汉字，全部能在 `hanchanlongcang.otf` 字形表里找到**（见 §四）。
- **验收闸门已就位**：接入前后都跑 `--script res://tools/verify_content.gd`
  —— 它检查"正解⊆词库 / 同槽无重复 / 故事含三个正解 / 报酬公式 / 称谓·正文·落款用字都有字形"，
  并抽样 1200 个 NPC（实测当前数据全过、152 个用字 0 缺字）。**扩充词库后它就是验收标准。**
- 工作量：改数据 + 改一处容器 + 重截 + 跑 `verify_content` / `verify_drop`（约半天）。

### 方案 B：收紧张力（只调数值，可与 A 叠加）

- **推荐档：目标 500 → 525**：完美/90% 不受影响（仍 100%），75% 命中从 69% → **47%**。
  这意味着"读得懂但偶有失误"的玩家要更认真，而高手依旧稳。
- 备选：目标 550（75% → 25%，偏硬核）。
- 不建议 `bonus × 0.75`：会把 75% 命中率打到 21%，惩罚的是中等玩家而不是"完美太宽"。
- 工作量：`PlayerManager.TARGET_MONEY` 一个常量 + 文档/README 同步 + 平衡报告更新。

### 方案 C：结构性改动（**不建议现在做**）

连续格式错误加倍扣钱、当日全错影响次日、委托人满意度等——都改玩法，
发布前动风险高，且需要重新定义"失败体验"。留到有真实玩家数据之后。

## 四、字体覆盖核对（为什么必须先查）

信纸上的称谓/正文/落款都用**寒蝉龙藏体**渲染，而它 CJK 覆盖率只有 **32.4%**。
一旦词里出现缺字，运行时靠 `FontFallback` 挂的系统字体兜底 —— 字能显示，
但**书法字里混进黑体**，信纸观感直接破。所以候选词先逐个撞 cmap：

```
$ python tools/check_content_chars.py
字体：hanchanlongcang.otf  字形表含 7038 个码位
候选条目：85 条，涉及汉字 181 个
[OK] 全部覆盖：候选里的每个汉字在字体里都有字形
```
